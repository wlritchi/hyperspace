# Hyperspace: wake a stopped session

Status: accepted. Date: 2026-10-28. This spec extends
[session status and liveness](2026-10-15-session-status.md) (the status spec).
It replaces the transport of "Messages to a session" in that spec. Terms such
as lease, liveness, heartbeat, launcher and wake kind have the meanings that
the status spec and the [main spec](2026-10-12-hyperspace.md) give.

## Problem

A session that waits for a message (`waiting` with wake `message`, or `ready`)
has no process on a runner (R2). When a message for it arrives, nothing
resumes it. The message waits until a user, or a boot of the runner, starts
the session.

The status spec makes the launcher the webhook that subspace calls. That does
not work: the launcher makes only outbound requests. A runner has no route in
from subspace, and a workstation is often behind NAT or off.

## Goals

- When a message arrives for a stopped session, the host that holds the lease
  resumes the session, in about two minutes.
- One path for every host kind: runners, and workstations that opt in.
- Hyperspace never reads or carries message content.
- Later events (PR events, crons that the server holds) can use the same path.

## Non-goals

- Addressing, handles, and durable mail. These are subspace's work. A session
  id is the only address that hyperspace knows.
- A `reopen` for a `done` session (M2), and notices to the sender. These stay
  in the status spec as later work.
- Starting a runner that does not run (scale to zero).
- A runner launcher mode that resumes only for wakes. At boot, a runner still
  resumes the sessions of R1, as the status spec says.

## How the pieces fit

```
sender ──message──▶ subspace
                      │ (no connection for the session after 60 s)
                      ▼
            POST /v1/wake/{harness}  ──▶  server: record a wake request
                                               │
             launcher on the lease host ◀──────┘ (its next tick reads
                      │                           its held sessions)
                      ▼
       claude --bg --resume <sid> "<fixed message>"
                      │
                      ▼
      relay in the session connects to subspace under <sid>
      and gives the messages to the agent
```

1. Subspace has a message for a session that has no connection. After a grace
   time (60 seconds in subspace), it sends a wake to the hyperspace server.
2. The server records a _wake request_ on the session and answers with a
   verdict.
3. At its next tick, the launcher of the host that holds the lease sees the
   pending request in its list of held sessions. It resumes the session.
4. The relay in the resumed session (a channel plugin) connects to subspace
   under the session id and puts the messages into the session.

The server is the meeting point, because each launcher already talks to it at
each tick. The wake needs no new connection to a host.

## Session identity

Subspace keys all of its state by session id. A resume must therefore continue
the session under the same id, so that the relay connects as the session that
the messages are for.

Hyperspace owns this rule for each resume that it does, on each host kind and
in each launcher mode. With Claude Code 2.1.301, `claude --bg --resume <sid>`
keeps the id, also when the daemon puts the job into a spare worker (checked
on 2026-10-26 and 2026-10-28). If a later Claude Code version breaks this,
hyperspace changes its resume.

## Server

### Wake endpoint

`POST /v1/wake/{harness}`, with a credential that has the new `wake` scope.
Subspace sends all the wakes of an account to one configured URL, so the
session id is in the body and not in the path:

```json
{
  "event": "wake",
  "account": "default",
  "session": "<session id>",
  "handle": "reviewer",
  "pending": 2,
  "items": []
}
```

The session is the credential's account, the harness of the path, and
`session`. The server does not use `account` or `handle` from the body, and it
ignores `items`. It can log the handle and `pending`.

| Session state                   | Response                                           |
| ------------------------------- | -------------------------------------------------- |
| Not found                       | `404`                                              |
| `done`                          | `409`, `message`: `session done: <note>`           |
| Lease `free`                    | `409`, `message`: `no host holds the session`      |
| `live` on a host                | `200`, `{"verdict": "live"}`. Records a request.   |
| Held, a launcher acts on wakes  | `200`, `{"verdict": "waking"}`. Records a request. |
| Other (also a `reserved` lease) | `200`, `{"verdict": "queued"}`. Records a request. |

- Each status other than `done` gets a wake, also `ready` and no status.
- The verdict is `waking` if a launcher that acts on wakes runs on the host
  that holds the lease: a heartbeat of that host with `wakes: true` has not
  expired. If not, it is `queued` (M3): for example a workstation without
  `--stay`, a runner with its own supervisor, or a runner that is down. The
  request is the same in both cases, and the session resumes when such a
  launcher runs.
- A `live` session also gets a request, because liveness can be one heartbeat
  old. If the process stopped, the launcher resumes the session.
- A `reserved` lease gets a request and the verdict `queued`. No launcher
  takes a reserved lease; a user restores the session on the target host, and
  that host's launcher then acts on the request. The server does not answer
  `503`, because subspace stops its retries after about 2.5 minutes.
- `409` means only "the state of the session refuses this wake". A
  configuration problem must not give `409`. The state can change later with
  no connection to subspace (a `reopen` or a restore from a shell), so a `409`
  refuses this wake only, not later wakes.

### Wake request

A session has at most one wake request: the time when the server received it,
and the `pending` count from the body. A new wake replaces it.

A request is _pending_ while the session is not `done` and no run of the
session started after the request. A _run_ starts when a heartbeat of a host
and source lists the session and the previous heartbeat of that source did not
list it. The server records the start time of the current run for each host
and source. The server calculates "pending" when it reads the session, as it
does for liveness. Thus nothing clears a request, and the launcher does not
acknowledge it: the first heartbeat that lists a new run ends it.

An expired heartbeat does not start a new run. This differs from the `since`
time of liveness, which starts again after a gap. A host that lost contact
with the server and still runs the process thus continues the same run. If the
process restarted during the gap, the server cannot see this. The request then
stays pending, and the session gets one more resume after that run stops.

A run that started before the wake does not end it, because its relay can be
disconnected. While that run is live, the launcher does not resume the
session. When it stops, the launcher resumes the session for the wake. If the
old run got its messages (its relay connected again), this resume is one turn
with no new messages. That cost is small, and a wake is not lost.

Status events do not change a request. A status write that the client queued
before the wake can arrive after it, so a status event cannot show that the
session saw the wake.

The session state and list entries have `wake_request` (`received` and
`count`) only while it is pending. `GET /sessions` gets the filter
`wake=pending`. `hyperspace ls` shows a pending wake next to the liveness.

A pending request has no expiry. A session that cannot resume on the lease
host (for example, it has no local copy there) keeps its request until it is
`done` or a run of it starts.

### The `wake` scope

A credential with `wake` can call only the wake endpoint. Give it no other
scope. Its `host` is a name for logs; it does not register a host.
`scripts/new-credential.py` can make such a credential. `GET /whoami`
advertises the capability `wake`.

A holder of a `wake` token can:

- make a launcher resume each open session whose lease a host holds, with a
  fixed first message;
- learn whether a session id exists in the account, whether the session is
  `done` and with which note, whether a host holds its lease, whether it is
  live, and whether a launcher that acts on wakes runs on the lease host.

It cannot read a transcript, add text of its choice to a session, or write a
status or a lease directly. Subspace has these powers already, because it
carries the messages.

## Launcher

### Which launchers act on wakes

- **Runner mode** (`--runner`): always. It already lists its held sessions at
  each tick.
- **Workstation mode with `--stay`**: yes. It lists its held sessions with
  `wake=pending` at each tick, and resumes a session only for a pending wake.
- **Workstation mode without `--stay`**: no. This launcher runs only while a
  session runs on the host, so its wakes would come at random times.

`--stay` is the opt-in on a workstation. With it, a message to a stopped
session starts that session as a background job on the workstation.

A launcher that acts on wakes sends `wakes: true` in each heartbeat. The
server keeps the time of the last such heartbeat for each host and source, and
the mark expires as a heartbeat does. The heartbeats of the SessionStart and
SessionEnd hooks do not send the field, and they do not change the mark.

### When a held session needs a process

The launcher resumes a held session that is not live, with a pending wake
request, whatever its status, also with no status. The rules of the status
spec still apply: the resume limit, no resume while a restore is pending or a
sync holds the lock, and no resume while the session runs on any host.

A failed resume leaves the request pending, so a later tick tries again.

### The first message

The first message has no message content, and it does not tell the agent to
get its messages: the relay gives them.

- If the session also needs a process for its status (runner mode, `working`,
  or `waiting` with wake `local`), the message is the status message of the
  status spec, with a fixed line after it.
- Otherwise, it is only the fixed line, for example
  `[hyperspace] Messages arrived while this session was stopped.`

### The relay

A resumed session gets its messages only if the relay loads as a channel. The
Claude Code options of the launcher (`launcher_claude_args`) must load it.
Runner images do this today. A workstation with `--stay` sets it in its client
configuration.

## Changes to other documents

- Status spec, "Messages to a session": the transport of this spec, and the
  rule of "Session identity". The launcher is not a webhook.
- Status spec, "Launcher": remove "receives wake requests" from the list of
  what the launcher does, or point it to this spec.
- `docs/runners.md`: replace "The launcher does not yet receive wake requests
  from subspace".
- `docs/deploy.md`: the `wake` credential for subspace, and the `--stay`
  launcher with the relay as a channel on a workstation.

## Later

- `reopen` for a `done` session (M2), and notices to the sender.
- Scale to zero: an operator starts a runner that does not run when one of its
  held sessions has a pending wake.
- Wakes for other events (PR events, crons that the server holds, other
  message sources), through the same endpoint and the same request.
