# Hyperspace: launch a session on a host

Status: accepted. Date: 2026-11-10. This spec extends the
[wake spec](2026-10-28-wake.md) and uses its terms, and those of the
[status spec](2026-10-15-session-status.md) and the
[main spec](2026-10-12-hyperspace.md).

## Problem

A session reaches a host only when someone starts it there by hand. On a
runner, that means a command in the runner's container. On a workstation,
`claude --bg` works, but the caller must give the right options and
environment, it does not learn the new session id in a form that it can use,
and nothing records which session started which.

Later, sessions must move between hosts with no command on the destination (a
push teleport). A launch is the same operation at turn 0: the destination
starts a session that it did not have before. Thus the launch is the first
part to build.

## Goals

- A caller starts a new session on a host of its account, with a prompt, and
  gets the session id at once.
- The same request starts a session on the caller's own host (a local launch).
- The destination needs no inbound connection. Its launcher picks up the
  request at its next tick, as it does for a wake.
- The new session records the session that started it (its parent).
- A push teleport can later use the same launcher path (see "Launch, wake and
  push teleport").

## Non-goals

- Push teleports. "Later" gives the plan, so that this design does not block
  it.
- Files, tools and other workspace state from the caller's host. The new
  session starts in a workspace on the destination, and it has only what is
  there.
- Launches into another account. The account is the security boundary (main
  spec, "Security").
- Starting a host that does not run (scale to zero).

## How the pieces fit

```
caller ──POST /v1/launch/{harness}──▶ server: record the session and a
  (gets the session id at once)               launch request for host H
                                                 │
                launcher on H ◀──────────────────┘ (its next tick lists
                      │                             its launch requests)
                      ▼
   claude --bg --session-id <sid> [options] "<prompt>"
                      │
                      ▼
   the first heartbeat that lists the run ends the request;
   the first sync uploads the transcript and holds the lease
```

1. The caller sends a launch request for host H. The server makes a new
   session id, records the session, with the lease `reserved` for H, and a
   launch request, and gives the id to the caller.
2. At its next tick, the launcher of H lists its pending launch requests and
   starts each session in a workspace on H.
3. The first heartbeat that lists a new run of the session ends the request,
   as a run ends a wake request. The first sync of the session uploads its
   transcript and takes the lease as held, because the lease is reserved for
   this host.

## Session identity

The server makes the session id (a random UUID) and gives it in the response.
Thus the caller knows the id before the session starts: it can send messages
to the session, and the parent link exists from the start. The launcher starts
the session with `claude --bg --session-id <sid>`.

The caller does not choose the id. A launch therefore always makes a new
session, and it cannot resume an existing one by mistake (see "Launch, wake
and push teleport").

A response can be lost, and the caller then sends the request again. To make
this safe, the request can have `request`, a random id that the caller makes.
The server keeps the `request` of each launch for 24 hours. A request with the
same `request` and the same fields gets the first response again, with the
same session id, and records nothing. A request with the same `request` and
other fields gets `409`.

Measurement M-1 (open): Claude Code 2.1.301 has `--session-id <uuid>` and
`--name <name>` (read from `claude --help` on 2026-11-10). Does it accept
`--session-id` with `--bg` and a prompt, start a job, and keep the id? If it
does not, the server cannot give the id at once, and this spec needs a step
that reports the id that Claude Code chose.

The id is a session id, so the rules of "Session identity" in the wake spec
apply: subspace addresses the new session by this id from its first turn.

## Launch, wake and push teleport

A wake, a launch and a push teleport do the same thing on the target: the
launcher starts a run of a session, with a first message, and first restores
the transcript if the host does not have it. The launcher has one code path
for this. The three requests differ in what the caller can choose, so they are
three requests with their own scopes, and not one request that resumes or
makes a session:

| Request       | Session                      | Host           | First message                |
| ------------- | ---------------------------- | -------------- | ---------------------------- |
| Wake          | Exists                       | The lease host | Fixed, no text of the caller |
| Launch        | New, with an id from server  | The caller's   | The caller's prompt          |
| Push teleport | Exists, the caller's session | The caller's   | Fixed: the host changed      |

A request that resumes an existing session with a prompt of the caller's
choice would put text into a session. That is a message, and messages are
subspace's work: subspace checks the senders, and the wake scope cannot add
text (wake spec, "The `wake` scope"). Also, a stale or wrong id would then
resume or reopen a session, and not fail.

## Server

### Launch endpoint

`POST /v1/launch/{harness}`, with a credential that has the new `launch`
scope:

```json
{
  "request": "<random id from the caller>",
  "host": "<target host>",
  "prompt": "<first prompt>",
  "workspace": "/home/claude/workspace",
  "model": "claude-opus-5-5",
  "effort": "high",
  "name": "reviewer",
  "parent": "<caller session id>"
}
```

- `host` and `prompt` are necessary. The others are optional.
- `prompt` is at most 64 KiB. The server keeps it only until the request ends,
  and then deletes it. The transcript has the prompt after that.
- `workspace` is an absolute path on the target. Without it, the launcher uses
  its default workspace.
- `model` and `effort` go to Claude Code as `--model` and `--effort`. Without
  them, Claude Code uses its defaults. A host's `launcher_claude_args` must
  not set them (they are in `_LAUNCHER_OWNS`).
- `name` goes to Claude Code as the display name of the job.
- `parent` must be a session id in the account. The server writes it into the
  session's first metadata as `links.parent` (see "Parent").

| Case                                     | Response                                                         |
| ---------------------------------------- | ---------------------------------------------------------------- |
| `parent` is not a session in the account | `400`                                                            |
| The host is not registered               | `404`, `detail`: `no such host`                                  |
| A known `request` with other fields      | `409`, `detail`: `request id used`                               |
| A known `request` with the same fields   | The first response again                                         |
| A launcher on the host acts on launches  | `200`, `{"session": "<id>", "verdict": "starting"}`. Records it. |
| Other                                    | `200`, `{"session": "<id>", "verdict": "queued"}`. Records it.   |

A launcher acts on launches if a heartbeat of the host with `launches: true`
has not expired. The verdict `queued` is not an error: the session starts when
such a launcher runs on the host.

### Launch request

A session has at most one launch request. The request is _pending_ while the
session is not `done` and no run of the session has started. A run starts as
the wake spec says ("Wake request"). Nothing clears the request, and the
launcher does not acknowledge it.

The session state and list entries have `launch_request` (`received`, `host`)
only while it is pending. `GET /sessions` gets the filter `launch=pending`.
`hyperspace ls` shows a pending launch in place of the liveness.

To cancel a pending launch, the caller marks the session `done`. A launch
request has no expiry.

### The `launch` scope

A holder of `launch` can make a launcher of any host in its account that acts
on launches start a session with a prompt of the holder's choice. That session
runs with the host's credentials (for example a forge token). Thus `launch` is
a scope of its own, and a host takes part only if its launcher opts in. Each
deployment decides which credentials get `launch`. For example, a fleet whose
agents start sessions on each other's runners gives it to workstations and to
runners. A deployment where a runner holds credentials that must stay apart
gives that runner's account no `launch` credential, or turns off `launches` on
its launcher.

One credential can have `launch` together with `append`, `read` and `grant`. A
credential that has `wake` cannot also have `launch`, because a `wake`
credential can call only the wake endpoint (wake spec, "The `wake` scope").
`GET /whoami` advertises the capability `launch`.

## Launcher

### Which launchers act on launches

The same launchers that act on wakes: runner mode, and workstation mode with
`--stay`. Such a launcher sends `launches: true` in each heartbeat. A launcher
can turn this off with `launches = false` in its configuration (for example a
runner whose host must only resume its own sessions).

### The start

At each tick, after `resume_held`, the launcher lists the sessions with
`launch=pending` and the lease reserved for its host, and starts each one:

```
claude [launcher options] [--model M] [--effort E] [--name N] \
  --bg --session-id <sid> "<prompt>"
```

- The launcher options and the environment are the same as for a resume
  (`launcher_claude_args`, `resume_env`).
- The workspace is the request's `workspace`, else the launcher's default. It
  must be an absolute path that exists on the host.
- The `max_sessions` limit and the resume limit apply.
- Before the start, the launcher saves the parent in local state, so that each
  metadata upload of the session keeps `links.parent`.

A start that fails for a reason that can change (a timeout, the session limit)
leaves the request pending, and a later tick tries again. A start that cannot
work (the workspace does not exist, Claude Code refuses an option) writes an
explicit `done` with the note `launch failed: <reason>`. That ends the
request, and the caller sees the reason with `hyperspace show`.

### Parent

The parent link uses the existing `links.parent` metadata and the
`child-sessions` capability. Thus `hyperspace show <parent>` lists the
launched session, and `hyperspace ls` hides it unless `--all`.

## Client

`hyperspace launch [--host H] [--workspace W] [--model M] [--effort E] [--name N] "<prompt>"`
sends a launch request and prints the new session id (`--json` prints the
response with the id).

- `--host` defaults to this host (a local launch).
- In a Claude Code session, the parent is the current session
  (`CLAUDE_CODE_SESSION_ID`).
- For a local launch on a host with no launcher that acts on launches (a
  workstation without `--stay`), the command sends the request as usual, and
  then runs one launcher pass for the launches of this host. That pass is the
  launcher's own code. Thus a local launch does not wait for a launcher, and
  there is only one way to start a launched session.

## Decisions

Recorded on 2026-11-10:

- The server makes the session id. A launch never resumes a session.
- Each deployment gives `launch` to the credentials that it chooses.
- A launch chooses its workspace with an absolute path, else the launcher's
  default workspace.
- A launch can set the model and the effort level.
- A local launch with no launcher runs one launcher pass, and has no start
  path of its own.

## Later

- **Push teleport.** A request of its own, with its own scope, on the same
  launcher path. The caller names its own session and a target host. The
  source host stops the session, syncs it, and surrenders the lease to the
  target (as `hyperspace teleport` does). The target's launcher restores the
  transcript and resumes the session with a fixed first message: the host or
  the working directory changed, and files from the old host are not there.
  Workspace state stays out of scope.
- **A note to the parent.** When a launched session becomes `done` and its
  parent session still exists, the parent gets a note about it by default.
- **Validation.** A runner's validation starts its first session with
  `hyperspace launch`, so that it uses the same path as production.
