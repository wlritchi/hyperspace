# Hyperspace: launch a session on a host

Status: accepted. Date: 2026-11-10. This spec extends the
[wake spec](2026-10-28-wake.md) and uses its terms, and those of the
[status spec](2026-10-15-session-status.md) and the
[main spec](2026-10-12-hyperspace.md).

## Problem

A session reaches a host only when someone starts it there by hand. On a
runner, that means a command in the runner's container. On a workstation,
`claude --bg` works, but the caller must give the right options and
environment, it does not learn the new session id in a form that it can use,
and nothing records which session started which.

Later, sessions must move between hosts with no command on the destination (a
push teleport). A launch is the same operation at turn 0: the destination
starts a session that it did not have before. Thus the launch is the first
part to build.

## Goals

- A caller starts a new session on a host of its account, with a prompt. It
  gets a launch id at once, and the session id when the session starts.
- A launch starts at most one session, also when other sessions start on the
  host at the same time.
- The same request starts a session on the caller's own host (a local launch).
- The destination needs no inbound connection. Its launcher picks up the
  request at its next tick, as it does for a wake.
- The new session records the session that started it (its parent).
- A push teleport can later use the same launcher path (see "Launch, wake and
  push teleport").

## Non-goals

- Push teleports. "Later" gives the plan, so that this design does not block
  it.
- Files, tools and other workspace state from the caller's host. The new
  session starts in a workspace on the destination, and it has only what is
  there.
- Launches into another account. The account is the security boundary (main
  spec, "Security").
- Starting a host that does not run (scale to zero).

## How the pieces fit

```
caller ──POST /v1/launch/{harness}──▶ server: record a launch L for host H
  (gets the launch id L at once)                 │
                launcher on H ◀──────────────────┘ (its next tick lists
                      │                             its pending launches)
                      ▼
       claim L, then: claude [options] --settings <marker L> \
         --bg -- "<prompt>"  ──▶ "backgrounded · <short>"
                      │
                      ▼
   the launcher links L to the new session id; the session's
   SessionStart hook links it too; the first sync uploads it
                      │
caller ◀── GET /v1/launch/{harness}/L: started, session <id>
```

1. The caller sends a launch request for host H. The server records a launch
   with a new launch id L, and gives L to the caller.
2. At its next tick, the launcher of H lists its pending launches. For each
   one, it claims the launch on the server, and then starts Claude Code in a
   workspace on H.
3. The launcher links L to the new session id, from the output of its own
   `claude --bg` (see "Which session a launch made"). The new session's
   SessionStart hook also links it, from an environment variable that the
   launcher gives to the job. The first sync of the session uploads its
   transcript and takes the lease, as for any new session.
4. The caller reads the launch, and gets the session id when the launch has
   started (`hyperspace launch --wait`).

## Session identity

Claude Code makes the id of a new background session. Measurement M-1 (on
2026-11-11, Claude Code 2.1.301): `claude --bg --session-id <uuid> "<prompt>"`
prints `--bg manages the session id; ignoring --session-id`, and starts a job
under a new id of its own. Thus no one knows the session id until the launcher
starts the session, and the server gives the caller a launch id in place of a
session id.

The caller gets the session id when the launch has started, usually within one
launcher tick. Until then, it cannot send messages to the new session. The id
is a session id, so the rules of "Session identity" in the wake spec apply:
subspace addresses the new session by this id from its first turn.

A launch always makes a new session, and it cannot resume an existing one (see
"Launch, wake and push teleport").

A response can be lost, and the caller then sends the request again. To make
this safe, the request can have `request`, a random id that the caller makes.
The server keeps the `request` of each launch for 24 hours. A request with the
same `request` and the same fields gets the first response again, with the
same launch id, and records nothing. A request with the same `request` and
other fields gets `409`.

## Launch, wake and push teleport

A wake, a launch and a push teleport do the same thing on the target: the
launcher starts a run of a session, with a first message, and first restores
the transcript if the host does not have it. The launcher has one code path
for this. The three requests differ in what the caller can choose, so they are
three requests with their own scopes, and not one request that resumes or
makes a session:

| Request       | Session                       | Host           | First message                |
| ------------- | ----------------------------- | -------------- | ---------------------------- |
| Wake          | Exists                        | The lease host | Fixed, no text of the caller |
| Launch        | New; its id is known at start | The caller's   | The caller's prompt          |
| Push teleport | Exists, the caller's session  | The caller's   | Fixed: the host changed      |

A request that resumes an existing session with a prompt of the caller's
choice would put text into a session. That is a message, and messages are
subspace's work: subspace checks the senders, and the wake scope cannot add
text (wake spec, "The `wake` scope"). Also, a stale or wrong id would then
resume or reopen a session, and not fail.

## Server

### Launch endpoint

`POST /v1/launch/{harness}`, with a credential that has the new `launch`
scope:

```json
{
  "request": "<random id from the caller>",
  "host": "<target host>",
  "prompt": "<first prompt>",
  "workspace": "/home/claude/workspace",
  "model": "claude-opus-5-5",
  "effort": "high",
  "name": "reviewer",
  "parent": "<caller session id>"
}
```

- `host` and `prompt` are necessary. The others are optional.
- `prompt` is at most 64 KiB. The server keeps it only until the launch is
  `started` or `failed`, and then deletes it. The transcript has the prompt
  after that.
- `workspace` is an absolute path on the target. Without it, the launcher uses
  its default workspace.
- `model` and `effort` go to Claude Code as `--model` and `--effort`. A host's
  `launcher_claude_args` can set them as defaults. The values of the launch
  replace these defaults. Without either, Claude Code uses its own defaults.
- `name` goes to Claude Code as the display name of the job.
- `parent` must be a session id in the account. The new session gets it as
  `links.parent` (see "Parent").

| Case                                     | Response                                                        |
| ---------------------------------------- | --------------------------------------------------------------- |
| `parent` is not a session in the account | `400`                                                           |
| The host is not registered               | `404`, `detail`: `no such host`                                 |
| A known `request` with other fields      | `409`, `detail`: `request id used`                              |
| A known `request` with the same fields   | The first response again                                        |
| A launcher on the host acts on launches  | `200`, `{"launch": "<id>", "verdict": "starting"}`. Records it. |
| Other                                    | `200`, `{"launch": "<id>", "verdict": "queued"}`. Records it.   |

A launcher acts on launches if a heartbeat of the host with `launches: true`
has not expired. The verdict `queued` is not an error: the launch starts when
such a launcher runs on the host.

### Launch states

A launch has one of these states:

| State       | Meaning                                                                  |
| ----------- | ------------------------------------------------------------------------ |
| `pending`   | No launcher has claimed it.                                              |
| `claimed`   | The launcher of the host claimed it and starts, or started, the session. |
| `started`   | A session is linked to it. The launch has `session`.                     |
| `failed`    | It did not start. The launch has `reason`.                               |
| `cancelled` | The caller cancelled it while it was `pending`.                          |

- `GET /v1/launch/{harness}/{launch}` gives the launch, with its state, and
  `session` or `reason`. A credential with `read` or `launch` can read the
  launches of its account.
- `DELETE /v1/launch/{harness}/{launch}` cancels a `pending` launch. A launch
  in another state gets `409`. To stop a launch that started, mark its session
  `done`.
- A launch that stays `claimed` with no linked session for 10 minutes becomes
  `failed`, with the reason `no session reported`.
- A `pending` launch has no expiry.

### The launcher's endpoints

A credential with `append` whose host is the launch's host can use these:

- `GET /v1/launch/{harness}?state=pending` lists the pending launches of the
  credential's host, with their fields.
- `POST /v1/launch/{harness}/{launch}/claim` changes `pending` to `claimed`. A
  launch in another state gets `409`. Thus a launch starts at most once, also
  when two processes of the host try to start it.
- `POST /v1/launch/{harness}/{launch}/link` with `{"session": "<id>"}` links a
  session to a `claimed` launch, and the state becomes `started`. A link of
  the same session again gets `200`. A link of another session gets `409`: the
  first link stays. A link to a `failed` launch that failed with
  `no session reported` is accepted, because the session can report late.
- `POST /v1/launch/{harness}/{launch}/fail` with `{"reason": "<one line>"}`
  changes `claimed` to `failed`.

### The `launch` scope

A holder of `launch` can make a launcher of any host in its account that acts
on launches start a session with a prompt of the holder's choice. That session
runs with the host's credentials (for example a forge token). Thus `launch` is
a scope of its own, and a host takes part only if its launcher opts in. Each
deployment decides which credentials get `launch`. For example, a fleet whose
agents start sessions on each other's runners gives it to workstations and to
runners. A deployment where a runner holds credentials that must stay apart
gives that runner's account no `launch` credential, or turns off `launches` on
its launcher.

One credential can have `launch` together with `append`, `read` and `grant`. A
credential that has `wake` cannot also have `launch`, because a `wake`
credential can call only the wake endpoint (wake spec, "The `wake` scope").
`GET /whoami` advertises the capability `launch`.

## Launcher

### Which launchers act on launches

The same launchers that act on wakes: runner mode, and workstation mode with
`--stay`. Such a launcher sends `launches: true` in each heartbeat. A launcher
can turn this off with `launches = false` in its configuration (for example a
runner whose host must only resume its own sessions).

### The start

At each tick, after `resume_held`, the launcher lists its pending launches.
For each one, while it is under the `max_sessions` limit, it does these steps:

1. It checks that the workspace (the launch's `workspace`, else its default)
   is an absolute path that exists on the host. If not, it claims the launch
   and fails it with the reason.
2. It claims the launch. If the claim gets `409`, it goes to the next launch.
3. It starts Claude Code in the workspace, with the launcher options
   (`launcher_claude_args`) and the environment marker in `--settings` (see
   "The environment marker"):

   ```
   claude [launcher options] [--model=M] [--effort=E] [--name=N] \
     --settings '{"env": {"HYPERSPACE_LAUNCH": "<launch id>",
                          "HYPERSPACE_LAUNCH_PARENT": "<parent>"}}' \
     --bg -- "<prompt>"
   ```

   The `--` makes sure that Claude Code does not read a prompt that starts
   with `-` as an option.

4. It finds the new session id (see "Which session a launch made"), saves
   `links.launch` and `links.parent` for that session in local state, and
   links the session to the launch on the server.

A launch starts at most once. After the claim, the launcher never runs
`claude --bg` for that launch again:

- If Claude Code exits with an error and makes no job, the launcher fails the
  launch with the first line of its output.
- If the launcher cannot find the session id (the output has no job id, the
  job has no state, or the state does not agree), it does not fail the launch
  and does not try again, because the session can have started. It logs an
  error. The session's own hook can still link it (see "The environment
  marker"). If nothing links it, the server fails the launch after 10 minutes.

### Which session a launch made

The launcher does not compare the job directories before and after the start.
Other launches, a user's `claude --bg`, or a `/background` can make job
directories at the same time, so a new directory does not show which start
made it.

The launcher takes the job id from the output of its own `claude --bg`
process. Claude Code 2.1.301 prints `backgrounded · <job id>`, or
`backgrounded · <job id> · <name>` with `--name` (seen on 2026-11-11). That
output is of this process only, so other starts on the host do not change it.
The launcher then reads `<config dir>/jobs/<job id>/state.json`. The session
id is its `sessionId`. The real path of the state's `cwd` must be the real
path of the launch's workspace, else the launcher does not link the session.
The launcher already reads this output after a resume, to find a copy
("started a copy as ...").

### The environment marker

The SessionStart hook of the new session sees `HYPERSPACE_LAUNCH` and
`HYPERSPACE_LAUNCH_PARENT` in its environment, because the launcher gives them
in the `env` of `--settings`. The launcher does not set them in the
environment of `claude --bg`: in Claude Code 2.1.301, a background job runs in
a process that the Claude Code daemon started before, with the environment of
the daemon, not of the `claude --bg` command (seen on 2026-11-11). If that
command starts the daemon, the daemon keeps its environment, so each later job
on the host would get the variables. If the host's `launcher_claude_args` has
its own `--settings`, the launcher does not add the marker, because the last
`--settings` replaces the others. It logs a warning, and only its own link
remains.

If the hook's `source` is `startup`, the hook saves `links.launch` and
`links.parent` for its session in local state, and the next sync links the
session to the launch on the server.

Thus the session itself reports which launch made it, also when the launcher
cannot read the output of Claude Code. The two reports must agree:

- The hook acts only on `startup`. A later resume of the session, or a
  `/background` copy that keeps the variable, does not report the launch.
- The hook acts only in the job that the launcher started: `CLAUDE_JOB_DIR`
  must name the job directory of the hook's session
  (`jobs/<the first 8 characters of the session id>`). The tools of the
  launched session give their environment to the processes that they start, so
  a `claude` that the session starts sees the variables too. A `claude` in the
  foreground (for example `claude -p`) keeps the job directory of the launched
  session, so it does not pass this check. A `claude --bg` or a `/background`
  copy gets its own job directory and passes it, but the launcher or the
  launched session usually links first.
- If the server refuses the link with `409`, the client removes the links of
  the marker from the local state of that session. The client does not try a
  link again after any `4xx`.
- The server keeps the first link. If the launcher and the hook give different
  sessions, the second link gets `409`, and the client logs an error.

### Parent

The parent link uses the existing `links.parent` metadata and the
`child-sessions` capability. Both the launcher and the hook save it in local
state, so that each metadata upload of the session keeps it (metadata is "the
latest event wins"). A restore of the session on another host (a fresh runner,
or a teleport target) takes `links.parent` and `links.launch` from the server
metadata, so that the first upload there keeps them too. Thus
`hyperspace show <parent>` lists the launched session, and `hyperspace ls`
hides it unless `--all`.

## Client

`hyperspace launch [--host H] [--workspace W] [--model M] [--effort E] [--name N] [--wait] "<prompt>"`
sends a launch request and prints the launch id. With `--wait`, it waits until
the launch is `started` or `failed`, and prints the session id or the reason.
`--json` prints the launch.

- `--host` defaults to this host (a local launch).
- In a Claude Code session, the parent is the current session
  (`CLAUDE_CODE_SESSION_ID`).
- For a local launch on a host with no launcher that acts on launches (a
  workstation without `--stay`, seen as the verdict `queued`), the command
  sends the request as usual, and then runs one launcher pass for only the
  launch that it made. That pass is the launcher's own code. Thus a local
  launch does not wait for a launcher, and there is only one way to start a
  launched session. The pass does not start other pending launches of the
  host, because the host did not opt in to the launches of other callers. If
  the pass does not claim the launch (for example at the `max_sessions`
  limit), the command cancels the launch and exits with an error, so that the
  prompt does not start later.
- The command prints the launch id to standard error as soon as the server
  records the launch, so that an error later does not hide it.
- `hyperspace launch --cancel <launch id>` cancels a pending launch.

## Decisions

Recorded on 2026-11-10 and 2026-11-11:

- A launch never resumes a session. The server makes a launch id, and Claude
  Code makes the session id (M-1).
- A launch starts at most once: the launcher claims it before the start.
- The launcher links a launch to its session from the output of its own
  `claude --bg`. The session's SessionStart hook links it too, from the
  environment marker. The server keeps the first link.
- Each deployment gives `launch` to the credentials that it chooses.
- A launch chooses its workspace with an absolute path, else the launcher's
  default workspace.
- A launch can set the model and the effort level.
- A local launch with no launcher runs one launcher pass for its own launch
  only, and has no start path of its own.

## Later

- **Push teleport.** A request of its own, with its own scope, on the same
  launcher path. The caller names its own session and a target host. The
  source host stops the session, syncs it, and surrenders the lease to the
  target (as `hyperspace teleport` does). The target's launcher restores the
  transcript and resumes the session with a fixed first message: the host or
  the working directory changed, and files from the old host are not there.
  Workspace state stays out of scope.
- **A note to the parent.** When a launched session becomes `done` and its
  parent session still exists, the parent gets a note about it by default.
- **Validation.** A runner's validation starts its first session with
  `hyperspace launch`, so that it uses the same path as production.
