# Wake a stopped session

This plan builds the [wake spec](../specs/2026-10-28-wake.md). The spec is the
source of truth for behavior. This plan sets the names and shapes that the
server and the client share, and the order of the work.

## Pieces

1. Protocol and server: the `wake` scope, the endpoint, the wake request, the
   run start, the wake mark of a heartbeat, and the list filter.
2. Client: the API calls, the launcher, and `hyperspace ls`.
3. Documents: the changes that the spec lists in "Changes to other documents",
   and the main spec (HTTP API, accounts files, security).

Piece 2 starts after piece 1, because its end-to-end tests need the server.
Piece 3 can run at the same time as piece 1.

## Shared names and shapes

### Protocol

- `Scope` gets `"wake"`.
- `HeartbeatRequest` gets `wakes: NotRequired[bool]`. `validate_heartbeat`
  accepts a boolean and keeps the field only when it is `true`.
- New `WakeRequestBody` (the request body of the endpoint) and
  `validate_wake_request`. Only `session` is required (a valid session id).
  `pending` is a non-negative integer (absent: 0). `handle` is a short string
  for logs, or absent. Ignore `event`, `account` and `items`, and do not
  refuse other fields.
- New `WakeVerdict = Literal["live", "waking", "queued"]` and
  `WakeResponse(TypedDict)`: `{"verdict": WakeVerdict}`.
- New `WakeRequest(TypedDict)`: `{"received": str, "count": int}`.
- `SessionStateBody` gets `wake_request: NotRequired[WakeRequest]`, present
  only while the request is pending.
- Release: `feat(protocol)`. The client needs the new protocol version.

### Server

- `lib/accounts.py`: `SCOPES` gets `"wake"`. A credential with `wake` and any
  other scope is an error when the accounts file loads.
  `scripts/new-credential.py` can make a `wake` credential.
- `CAPABILITIES` gets `"wake"`.
- `POST /v1/wake/{harness}`: only a `wake` credential can call it, and a
  `wake` credential can call only this endpoint. The responses are the table
  in the spec. Log the session, the handle, `pending` and the verdict.
- New migration:
  - Table
    `wake_requests (session PRIMARY KEY REFERENCES sessions (id), received, count)`.
    A new wake replaces the row. Purge deletes the row. A wake does not make a
    restore stale.
  - `session_liveness` gets `run_started TEXT`. A heartbeat sets it to `now`
    when the row is new, or when the previous heartbeat of the source did not
    list the session (`last_listed < previous.received`). Expiry of the
    previous heartbeat does not count. For old rows, the migration copies
    `first_listed`.
  - `host_heartbeats` gets `wakes_received TEXT` and `wakes_interval INTEGER`.
    A heartbeat with `wakes: true` sets them. A heartbeat without the field
    does not change them. A `final` heartbeat clears them.
- Pending: the session is not `done`, and no `session_liveness` row of the
  session has `run_started > received`. Calculate it where the store makes the
  session state, and in SQL for the filter `wake=pending` of `GET /sessions`.
- Verdict `waking`: the lease is `held`, and a heartbeat of the lease host
  (any source) has `wakes_received` that has not expired
  (`HEARTBEAT_EXPIRY * wakes_interval`).

### Client

- `api.py`: `wake(harness, body)`, and the `wake` filter for the lists.
- `send_heartbeat` gets `wakes: bool`. The launcher sends `wakes: true` in
  runner mode and with `--stay`. The hooks do not send it.
- `needs_process` also returns a first message for a held session that is not
  live and has `wake_request`, whatever its status. The message is the status
  message (runner mode only) followed by a fixed line, or the fixed line
  alone. Name the fixed line `RESUME_WAKE`.
- Workstation with `--stay`: at each tick, list the held sessions with
  `wake=pending` and resume each one that `needs_process` accepts. Do this
  only if the server advertises the capability `wake`. Runner mode keeps its
  list of held sessions, which now also shows `wake_request`.
- The decision always uses the `wake_request` field, not only the filter. A
  server that does not know the filter then cannot cause a resume.
- `hyperspace ls`: show a pending wake next to the liveness.

## Tests

- Unit tests for the store: pending and its end by a new run; a heartbeat gap
  that is not a new run; a run that started before the wake; `done` ends
  pending; the filter; each verdict; the wake mark and its expiry; a hook
  heartbeat that does not change the mark; a `final` heartbeat.
- End-to-end tests for the endpoint: the scope rules, 404, each 409, each 200.
- Launcher tests with `fake_claude.py`: runner mode resumes for a wake; a
  workstation with `--stay` resumes only for a wake; a workstation without
  `--stay` does not; the first messages; no resume while live.
